# Audit transversal de Kapsule

> Date de l'audit : 2026-07-18
> Version auditee : `main` a `1cf2ed0`
> Perimetre : produit, UX/UI, performances, accessibilite, documentation publique,
> ingenierie, exploitation, licence et securite.

## Synthese executive

Kapsule est un MVP fonctionnel et lisible. Le contrat JSON est strict, le parcours
principal fonctionne de l'import a la revision espacee, les droits sont explicites,
la base SQLite est migree proprement et le deploiement est documente. Le build web
reste compact : 181,43 kB de JavaScript, soit 58,86 kB gzip.

Le depot n'est toutefois pas pret a etre considere comme un service public durci.
Les principaux risques concernent l'inclusion possible d'une cle SSH locale dans
le contexte Docker, le cache PWA partage entre comptes, l'acces public aux assets
de decks prives et des controles de visibilite incomplets sur les ecritures de
progression/revision. L'absence de CI, de protection de `main` et de fichier de
licence aggrave le risque de regression et laisse la declaration MIT incomplete et
non detectee par GitHub.

| Axe | Maturite | Conclusion |
| --- | --- | --- |
| Fonctionnalites | 7/10 | MVP coherent, quelques promesses incompletes et parcours operateur fragiles |
| Design et UX | 6/10 | Interface claire et responsive, mais peu outillee pour l'echelle et les erreurs |
| Performances | 7/10 | Front leger et SQLite adapte au volume actuel, contention future cote serveur |
| Accessibilite | 4/10 | Bonne base semantique, mais pas de preuve WCAG ni de gestion du focus/statuts |
| README et GitHub | 4/10 | Demarrage rapide correct, vitrine et gouvernance publique incompletes |
| Rigueur d'ingenierie | 4/10 | Tests et Logics solides, mais aucune barriere automatisee avant fusion |
| Securite | 3/10 | Plusieurs risques inter-comptes et operationnels a corriger avant exposition large |

Verdict : utilisable comme MVP controle, mais durcissement P0/P1 requis avant
d'augmenter le nombre d'utilisateurs ou d'ouvrir durablement les inscriptions.

## Methode et preuves

L'audit repose sur une lecture du code et des documents, l'inspection de Git et de
GitHub, ainsi que les commandes suivantes :

- `npm test` : schema 10/10, frontend smoke OK, backend 34/35 dans l'arbre de
  travail audite ; le test en echec depend d'un score de quiz code en dur et casse
  lorsque le deck exemple passe de 2 a 6 questions.
- `npm run build` : succes ; bundle principal 181,43 kB, 58,86 kB gzip ; precache
  PWA 188,70 KiB.
- `npm audit --omit=dev` : 0 vulnerabilite de production connue.
- `npm audit` : 2 alertes d'outillage, une elevee sur Vite 5 et une moderee sur
  esbuild.
- `logics-manager health` : 22 documents, aucun signal d'anomalie au debut de
  l'audit.
- GitHub Community Profile : 28 %, aucune licence detectee, aucun guide de
  contribution, template d'issue ou code de conduite ; `main` non protegee.

Deux modifications de decks etaient deja presentes avant l'audit. Elles ne font
pas partie de ses livrables. Le test rouge est neanmoins un signal valide : un test
metier ne devrait pas dependre du nombre courant de questions d'un contenu exemple.

## Fonctionnalites et rigueur metier

### Points solides

- Le format de deck est ferme par JSON Schema, borne en taille et complete par des
  validations metier, notamment l'unicite des fiches et l'index de bonne reponse.
- Le parcours couvre inscription, connexion multi-appareils, import, lecture,
  progression, quiz, repetition espacee SM-2, roles et visibilite.
- Les migrations SQLite sont versionnees et transactionnelles. Les cles et index
  principaux sont adaptes au MVP.
- Les regles de permission sont isolees dans des fonctions pures et largement
  testees pour le listing, la lecture, la creation et l'administration.
- Le corpus Logics conserve les besoins, ADR, criteres d'acceptation et preuves de
  livraison. C'est un bon niveau de tracabilite pour un depot de cette taille.
- Sauvegarde SQLite coherente en WAL, rotation et procedure de restauration sont
  documentees.

### Defauts et ecarts

| Severite | Constat | Impact / preuve |
| --- | --- | --- |
| Haute | Les ecritures de progression et de revision n'appellent pas `canViewDeck` | Un compte authentifie peut ecrire sur une fiche cachee s'il connait `deckId/cardId` (`apps/backend/src/app.mjs:203`, `apps/backend/src/app.mjs:224`) |
| Haute | La liste des revisions dues ne refiltre pas la visibilite courante | Un deck devenu prive ou master peut continuer a exposer ses titres via une ancienne revision (`apps/backend/src/store.mjs:270`) |
| Haute | La suite backend depend du contenu mutable de `decks/reseaux-essentiels.json` | `quizScore: 2` represente un succes avec 2 questions, un echec avec 6 (`apps/backend/test/reviews.test.mjs:89`) |
| Moyenne | La promesse hors-ligne est partielle | Les GET sont caches, mais les ecritures optimistes ne sont ni persistees localement ni rejouees ; une erreur est seulement envoyee en console (`apps/frontend/src/pages/DeckReader.jsx:57`) |
| Moyenne | Une revision avance avant confirmation serveur | Une requete perdue n'est pas retentee et l'utilisateur voit quand meme la session terminee (`apps/frontend/src/pages/ReviewSession.jsx:74`) |
| Moyenne | Les roles ne sont administrables que par SQL | Le fonctionnement depend d'une intervention de production non reproductible depuis l'application |
| Moyenne | Aucun flux d'upload d'assets n'accompagne l'import JSON | Le schema accepte des chemins relatifs, mais l'interface n'importe qu'un fichier JSON ou du texte |
| Moyenne | Le script de deploiement a un chemin distant par defaut invalide | `cd "~/kapsule"` n'expanse pas le tilde (`deploy/deploy.sh:13`, `deploy/deploy.sh:22`) |
| Moyenne | `.env.example` est cite mais ignore et non versionne | Une nouvelle installation ne dispose pas du fichier demande par `deploy/README.md` |
| Faible | Le brief produit reste `Proposed` et ses non-objectifs sont depasses | Il exclut les decks prives et la repetition espacee alors qu'ils sont livres |

Le modele de donnees gagnerait aussi a relier `progress` et `reviews` aux comptes et
aux fiches par des cles etrangeres. Aujourd'hui, les cascades reposent sur les
operations applicatives et des lignes orphelines restent possibles.

## Design et experience utilisateur

### Points solides

- Le parcours principal est court et la hierarchie visuelle est facile a scanner.
- Les vues sont responsive, avec largeur de lecture bornee, grille adaptative et
  prise en charge automatique du theme sombre.
- Les etats de deck, badges de visibilite, progression et revision donnent un
  retour immediat sans surcharger l'ecran.
- Les formulaires reposent majoritairement sur des controles HTML natifs.

### Limites

- La palette et la composition sont tres generiques ; la marque se reduit a un
  monogramme et le produit n'a ni capture ni demonstration visuelle publique.
- Il manque recherche, filtre, tri et regroupement pour une bibliotheque de decks
  importante. Le contrat accepte jusqu'a 200 fiches par deck sans navigation
  secondaire ni sommaire filtrable.
- Une suppression est immediate, sans confirmation ni possibilite d'annulation
  (`apps/frontend/src/pages/DeckReader.jsx:29`).
- Les erreurs remplacent souvent toute la vue et il n'existe pas d'action de retry.
- L'etat d'une fiche n'est pas represente dans l'URL : retour navigateur, partage
  d'un lien et reprise precise sont limites.
- Les boutons utilisent du texte et des symboles Unicode de facon heterogene ; il
  n'existe pas de systeme d'icones ou de composants documente.

## Performances et scalabilite

### Points solides

- Le bundle initial est raisonnable et aucune dependance UI lourde n'est chargee.
- Les images sont chargees paresseusement et Caddy active gzip/zstd en production.
- Les acces SQLite utilisent des requetes preparees et les index essentiels pour
  les sessions, proprietaires et echeances de revision.
- Le frontend est pre-cache et les lectures de decks utilisent `NetworkFirst`.

### Risques

- `scryptSync` bloque la boucle evenementielle a chaque inscription et connexion.
  Sans limite de debit, quelques requetes concurrentes peuvent degrader toute l'API
  (`apps/backend/src/auth.mjs:12`, `apps/backend/src/auth.mjs:24`).
- Chaque requete authentifiee prolonge la session par une ecriture SQLite. Les
  lectures deviennent donc des ecritures et augmentent la contention
  (`apps/backend/src/auth.mjs:122`).
- Les sessions expirees ne sont purgees que lorsqu'un ancien jeton est reutilise.
- Un deck complet est stocke une fois comme JSON puis chaque fiche est dupliquee
  dans `cards`; la lecture charge et parse le deck entier, sans pagination.
- Le schema autorise une source d'image de 3 Mo et le corps JSON global 5 Mo. Les
  data URI gonflent a la fois la base, les reponses et le cache navigateur.
- Il n'existe ni budget de performance, ni test de charge, ni metrique de latence,
  ni observabilite applicative.

Pour le volume actuel, ces choix restent acceptables. Les deux corrections les plus
rentables sont le hachage asynchrone avec limitation de debit, puis la reduction des
ecritures de rafraichissement de session.

## Accessibilite

### Points solides

- La page declare `lang="fr"`, utilise des titres, liens, listes et boutons natifs.
- Les champs email et mot de passe ont des labels et des attributs `autocomplete`.
- Les images passent un texte alternatif et les informations ne dependent pas
  toutes uniquement de la couleur.

### Ecarts WCAG probables

| Severite | Constat | Remediation attendue |
| --- | --- | --- |
| Haute | Aucun test automatise axe/Lighthouse ni parcours clavier documente | Ajouter des tests sur les vues critiques et une verification manuelle WCAG 2.2 AA |
| Haute | Le resultat des quiz n'est pas annonce aux technologies d'assistance | Ajouter un statut live et un libelle explicite correct/incorrect ; ne pas masquer toute l'information avec `aria-hidden` |
| Moyenne | Aucun focus de route ou focus apres changement de fiche | Deplacer le focus sur le titre principal et gerer le titre de document |
| Moyenne | Aucun style `:focus-visible` explicite | Garantir un indicateur de focus coherent et contraste sur tous les controles |
| Moyenne | Chargements, erreurs et succes d'import ne sont pas des live regions | Utiliser `role="status"` ou `role="alert"` selon le cas |
| Moyenne | La barre de progression n'expose pas `role=progressbar` et ses valeurs | Fournir `aria-valuemin`, `aria-valuemax` et `aria-valuenow` |
| Moyenne | Les animations ne respectent pas `prefers-reduced-motion` | Desactiver les transitions pour les utilisateurs concernes |
| Faible | Aucun lien d'evitement vers le contenu principal | Ajouter un skip link visible au focus |

Une campagne de contraste sur themes clair et sombre reste necessaire, notamment
sur les textes attenues, badges et etats de boutons desactives.

## README et presentation GitHub

Le README explique correctement la proposition de valeur, le monorepo, le
demarrage, la validation d'un deck et le lien vers le deploiement. Il est cependant
insuffisant pour un depot public :

- `npm test` est decrit comme le seul test du contrat alors qu'il lance tous les
  workspaces ; l'etat reel et les prerequis Node/npm ne sont pas detailles.
- Aucun screenshot, GIF, URL de demonstration ou schema de parcours n'illustre le
  produit.
- Authentification, roles, SM-2, fonctionnement hors-ligne et limites connues ne
  sont pas presentes dans la liste des fonctionnalites.
- Il manque les sections configuration, variables d'environnement, architecture,
  securite, contribution, licence et support.
- Aucun badge CI, build, licence ou version ne donne un signal de sante.

Cote GitHub, la description est pertinente mais le depot n'a ni homepage, ni
topics, ni licence detectee, ni templates communautaires. Le score Community
Profile observe est de 28 %. La branche `main` n'est pas protegee et aucun workflow
GitHub Actions n'est present. Le wiki est active sans etre utilise par le depot.

## Rigueur d'ingenierie, CI et licence

### Acquis

- Monorepo npm verrouille par `package-lock.json` et versions de runtime declarees.
- Tests unitaires, API, permissions, import de bout en bout et smoke SSR.
- Migrations, sauvegarde/restauration, ADR et criteres d'acceptation documentes.
- Separation correcte entre schema, stockage, permissions, API et composants UI.

### Manques bloquants

- Aucune CI n'impose tests, build, lint, audit ou validation des decks sur une PR.
- Aucun linter, formatter, analyse statique, couverture minimale ou test navigateur.
- `main` accepte les pushes directs et n'exige aucun check.
- Aucun Dependabot/Renovate, scan de secrets, CodeQL ou scan d'image Docker.
- Le package racine declare `MIT`, mais aucun fichier `LICENSE` n'existe et GitHub
  ne detecte donc aucune licence. La declaration dans `package.json` ne remplace pas
  le texte de licence et son attribution.
- Aucun `SECURITY.md`, guide de contribution, politique de versions, changelog ou
  procedure de signalement responsable.
- Des adresses email personnelles de production sont conservees dans les documents
  Logics publics ; ces preuves devraient utiliser des identifiants non personnels
  ou etre placees dans un registre d'exploitation prive.

## Securite

### P0 - Secret potentiellement copie dans Docker

Une cle privee SSH de deploiement est presente localement et correctement ignoree
par Git. Elle n'apparait pas dans l'historique inspecte. En revanche,
`.dockerignore` n'exclut ni `cle_hetzner`, ni sa cle publique, ni
`.deploy_known_hosts`, et le Dockerfile execute `COPY . .` dans l'etape de build.
La cle peut donc etre envoyee au daemon et persister dans le cache ou une couche
intermediaire. Il faut exclure explicitement les secrets, passer a des `COPY`
cibles, nettoyer les caches concernes et faire tourner la cle par precaution.

### P1 - Isolation entre utilisateurs

- Le service worker met en cache `/api/decks...` uniquement par URL. Les reponses
  portent un Bearer token mais le cache n'est ni segmente par utilisateur ni purge
  au logout. Hors ligne, un compte B sur le meme navigateur peut recevoir les decks
  du compte A (`apps/frontend/vite.config.mjs:33`, `apps/frontend/src/api.js:8`).
- La route d'assets est publique et ne verifie pas la visibilite du deck. Les images
  d'un deck prive sont accessibles avec un chemin connu
  (`apps/backend/src/app.mjs:84`).
- Les routes progression/revision ne controlent pas `canViewDeck`, et les revisions
  dues ne refiltrent pas les droits courants.

### P1 - Authentification et abus

- Aucun rate limit, ralentissement progressif ou verrouillage ne protege login et
  register. Avec `scryptSync`, cela permet brute force et deni de service CPU.
- Les inscriptions sont ouvertes par defaut dans Docker Compose. Une erreur de
  configuration expose immediatement la creation de comptes.
- Les jetons de session durent 90 jours glissants, sont stockes en clair dans
  SQLite et dans `localStorage`. Un XSS ou une fuite de base donne un jeton actif.
- Aucune limite maximale de mot de passe n'est appliquee avant le hachage.

### P1/P2 - Chaine logicielle et HTTP

- Vite 5.4.21 est concerne par une alerte elevee de traversee de chemin et esbuild
  par une alerte moderee sur le serveur de developpement. Les dependances de
  production sont propres selon `npm audit --omit=dev`, mais l'outillage doit etre
  mis a niveau et ne jamais etre expose au reseau public.
- CORS accepte toutes les origines, Express expose ses en-tetes par defaut et aucune
  politique CSP/HSTS/referrer/permissions n'est definie explicitement.
- Le conteneur applicatif s'execute en root, sans healthcheck, limites de ressources,
  filesystem en lecture seule ni reduction de capabilities.
- Les images Caddy et Node sont referencees par tags mouvants, sans digest ni outil
  de scan.
- Les sauvegardes restent sur le meme VPS et aucune preuve periodique de restauration
  ou copie hors site n'est automatisee.

## Plan de correction recommande

### P0 - Immediat

1. Exclure toutes les cles et secrets du contexte Docker, utiliser des copies
   ciblees, inspecter/purger les caches de build et faire tourner la cle observee.
2. Desactiver le cache runtime des API authentifiees jusqu'a disposer d'un cache
   segmente et purge a chaque changement de session.
3. Proteger les assets, progression, revisions et liste des dues avec la meme
   decision d'autorisation que la lecture du deck.

### P1 - Avant nouvelle ouverture publique

1. Ajouter rate limiting, hachage non bloquant, politique de session et inscription
   fermee par defaut.
2. Mettre en place une CI obligatoire : lint, tests, build, audit, scan de secrets,
   scan de dependances et tests d'autorisation negatifs.
3. Ajouter `LICENSE`, `SECURITY.md`, mise a niveau Vite et protection de `main`.
4. Corriger le deploiement reproductible : `.env.example` versionne, chemin distant,
   healthchecks, utilisateur non-root et en-tetes HTTP.

### P2 - Qualite et croissance

1. Rendre les tests independants des decks de demonstration et fixer un seuil de
   couverture.
2. Atteindre WCAG 2.2 AA sur auth, liste, lecture, quiz, import et revision.
3. Ajouter recherche/tri, retry/synchronisation hors-ligne et confirmation des
   actions destructrices.
4. Mettre a jour README, brief produit et metadata GitHub avec captures, demo,
   architecture, statut CI, contribution et limites connues.
5. Definir budgets de performance, metriques, sauvegarde hors site et test de
   restauration regulier.
